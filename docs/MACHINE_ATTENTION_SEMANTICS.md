# Machine Attention의 의미론 — 무엇을 측정하고, 무엇을 측정하지 않는가

`machine_events`와 `machine_score`를 어떻게 읽어야 하는지에 대한 문서.
한 문장으로: **이 장치는 "어떤 자동화된 주체가 사이트를 방문했는가"의 관측 장치이지,
"AI가 내 글을 학습·검색·답변에 사용했는가"의 성과 지표가 아니다.**

---

## AI가 URL을 다루는 세 가지 경로

AI 서비스마다 URL 처리 방식이 다르고, 그중 사이트 로그에 잡히는 것은 하나뿐이다.

| 경로 | 흐름 | 로그 |
|---|---|---|
| ① 직접 fetch | 사용자 → AI → **내 사이트** | **남는다** — ChatGPT-User, Claude-User, Gemini Deep Research 등 |
| ② 색인 이용 | 사용자 → AI → 자체/검색 색인 → 과거에 수집된 콘텐츠 | 질문 시점에는 **안 남는다** — 소비자 Gemini 앱이 대표적 |
| ③ 제3자 중간층 | 사용자 → AI → 검색 API·캐시·proxy → 내 사이트 | 실제 요청 시점을 로그만으로 **특정할 수 없다** |

②③이 존재하는 한, access log는 AI 참조 전체의 관측 방법이 될 수 없다.

## 로그가 증명하는 범위

로그 한 줄이 증명하는 것은 정확히 여기까지다:

> "이 URL에 HTTP 요청이 있었다."

그 이후 — "이 콘텐츠가 답변 생성에 실제로 사용되었다" — 는 별개의, 관측 불가능한 문제다. 따라서:

- **로그가 없다 ≠ 참조하지 않았다** (경로 ②③)
- **로그가 있다 ≠ 답변에 사용했다** (fetch 후 버렸을 수 있다)

이 두 해석 금지는 어떤 실험 결과를 기록할 때도 유지한다.

## 그래서 `machine_score`는 무엇인가

`machine_score`(= `ai` 카테고리, 사용자 질문을 대리한 fetch)는 **"AI 참조 전체"가 아니라
그중 경로 ①로 도달한, 좁고 정직한 표본**이다. 전체 참조량의 하한(lower bound)으로 읽어야 하며,
서비스 간 비교 지표로 쓰면 안 된다 — 경로 ①을 쓰는 서비스(ChatGPT, Claude)가
경로 ②를 쓰는 서비스(소비자 Gemini)보다 참조를 많이 하는 것처럼 보이는 것은
측정 방식의 차이지 실제 참조량의 차이가 아니다.

데이터는 세 층으로 관리된다:

```
machine_events  = 관찰 원본. 모든 fetch가 append-only로 보존된다.
machine_access  = 실측 fetch 횟수. 요청 즉시 누적.
machine_score   = AI attention 해석. 요청 즉시의 잠정값을,
                  밤의 sleep rebuild가 원본에서 재계산해 정본화한다.
```

정본화 규칙: **(agent, record, UTC일) 그룹당 1회**, 그룹 내 최고 confidence × 0.30.
한 대화에서 같은 글을 다섯 번 fetch해도 "그날 이 agent가 이 Record에 관심을 보였다"는
하나의 사실이고, confidence는 그 분류를 얼마나 확신하는가다. access와 score가 의도적으로
갈라지므로(4연타 = access +4, score +0.30), 나중에 "AI가 몇 번 가져갔는가"와
"몇 번의 독립적 관심으로 간주하는가"를 분리해 볼 수 있다.

같은 이유로 **crawler 관측 로그를 프로젝트의 성과 지표로 삼지 않는다.**
이 장치의 가치는 "인터넷의 어떤 자동화된 주체들이 실제로 방문하는가"라는
지형 관찰 자체에 있고, 그 관찰이 타일의 색과 선명도가 된다.

## 통제할 수 있는 것은 여기까지다

AI에게 발견되고, 읽히고, 출처로 식별될 수 있는 웹 자산을 만들어 두는 것까지가 통제 범위다.

1. **발견 가능성** — sitemap, RSS, robots.txt, 독립적인 Record URL, 검색엔진 등록, 외부 링크
2. **가독성** — 본문이 정적 HTML에 존재, 의미 있는 `<title>`/description/heading, 실제 `<a>` 링크
3. **출처 식별성** — 제목·저자(사이트 정체성)·날짜·canonical URL이 HTML 안에 명확히 존재.
   AI가 내용을 가져가더라도 "어디에서 온 내용인지" 식별할 수 있게 하는 것.
   (현재: title/og:site_name/published_time/canonical 구현됨. JSON-LD Article은 미구현 — 선택 레버로 남아 있다.)

그 다음 — 어떤 AI가 언제 어떤 색인을 통해 콘텐츠를 가져가고 실제 답변에 썼는지 — 는
상당 부분 관측 불가능한 영역이며, 그 사실을 받아들이는 것이 이 문서의 요지다.

## 의미 있는 평가 방법: 출처 등장 테스트

로그 감시 대신, **검색 결과와 AI 답변에서 Record가 출처로 등장하는지를 주기적으로 직접 테스트**한다.

프로토콜:

1. 동일한 Record URL을 Gemini / ChatGPT / Claude / Perplexity에 각각 제공
2. 동일한 질문: "이 글에서 저자가 주장하는 X를 설명하고, 원문의 논리를 비판하라"
3. 세 가지를 기록: **읽었는가**(내용을 실제로 반영했는가) / **사이트 요청이 로그에 남았는가** / **출처를 표시했는가**

| 일자 | 서비스 | Record | 읽음 | 실제 요청 로그 | 출처 표시 | 비고 |
|---|---|---|---|---|---|---|
| 2026-08-13 | Gemini | post_ | 읽음 | 없음 | ? | 색인/캐시 경로로 추정 |
|  |  |  |  |  |  |  |

기록 시 주의: "요청 로그 없음"은 경로 ②③의 증거일 뿐 미참조의 증거가 아니다.
