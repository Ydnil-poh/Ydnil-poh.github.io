# Machine Attention의 의미론 — 무엇을 측정하고, 무엇을 측정하지 않는가

`machine_events`와 `machine_score`를 어떻게 읽어야 하는지에 대한 문서.
한 문장으로: **이 장치는 "어떤 자동화된 주체가 사이트를 방문했는가"의 관측 장치이지,
"AI가 내 글을 학습·검색·답변에 사용했는가"의 성과 지표가 아니다.**

---

## AI가 URL을 다루는 세 가지 경로

AI 서비스마다 URL 처리 방식이 다르고, 그중 사이트 로그에 잡히는 것은 하나뿐이다.

| 경로 | 흐름 | 로그 |
|---|---|---|
| ① 직접 fetch | 사용자 → AI → **내 사이트** | **자기 식별하는 agent만 남는다** — ChatGPT-User, Claude-User 등. 브라우저형 UA의 비식별 fetcher는 같은 경로인데도 안 남는다 (아래 실증) |
| ② 색인 이용 | 사용자 → AI → 자체/검색 색인 → 과거에 수집된 콘텐츠 | 질문 시점에는 **안 남는다** — 소비자 Gemini 앱이 대표적 |
| ③ 제3자 중간층 | 사용자 → AI → 검색 API·캐시·proxy → 내 사이트 | 실제 요청 시점을 로그만으로 **특정할 수 없다** |
| ④ 다른 표면 | 사용자 → AI → **GitHub 저장소** (같은 콘텐츠의 다른 공개 표면) | **관측 범위 밖** — 요청이 github.com으로 가므로 사이트 로그에 안 남는다 |

②③④가 존재하는 한, access log는 AI 참조 전체의 관측 방법이 될 수 없다.

④는 실측으로 확인됐다 (2026-08-13): ChatGPT에 "내 사이트의 22번 포스트 확인해줘"라고
하자 본문·frontmatter를 정확히 읽고 **"GitHub의 main 기준으로 확인했어"** 라고 출처를 밝혔다.
`machine_events`에는 아무것도 남지 않았고, 그게 정확한 동작이다 — 접근이 없었던 게 아니라
관측하지 않는 표면에서 접근이 일어난 것이다. 저장소는 공개 상태를 유지한다: github.com은
이미 깊이 색인된 고권위 도메인이라 그 자체로 발견 채널이며, 이를 닫아 관측 순도를 올리는 것보다
발견 가능성이 우선이다. 관측 장치는 사이트 표면만 커버한다는 사실을 받아들인다.

①의 사각도 실측으로 확인됐다 (2026-08-25, 통제 실험): 어떤 AI 대화·외부 링크에도 노출된 적
없는 레코드(post4)의 URL을 네이버 AI에 주자 본문을 단어 수준으로, 페이지 메타데이터(게시일)까지
정확히 재현했다 — 실시간 fetch 없이는 불가능한 결과다. 그런데 `machine_events`(분류·검증 봇)와
`archive_events`(클라이언트 JS) **양쪽 모두 무기록**이었다. 미들웨어는 KNOWN_AGENTS 매칭 또는
Cloudflare 검증 봇만 기록하므로, 브라우저형 UA를 쓰는 미검증 fetcher는 경로 ①(직접 fetch)을
타면서도 구조적으로 비가시다. 대응은 전 요청 로깅(관측 확장)이 아니라 이 사각의 문서화다 —
확장하면 인간 방문자의 UA까지 수집하게 되는데, 위장 UA는 어차피 인간과 구별할 수 없어서
사각은 줄어들 뿐 사라지지 않는다. machine_score의 하한선 성격은 경로 ①에도 적용된다.

## 로그가 증명하는 범위

로그 한 줄이 증명하는 것은 정확히 여기까지다:

> "이 URL에 HTTP 요청이 있었다."

그 이후 — "이 콘텐츠가 답변 생성에 실제로 사용되었다" — 는 별개의, 관측 불가능한 문제다. 따라서:

- **로그가 없다 ≠ 참조하지 않았다** (경로 ②③)
- **로그가 있다 ≠ 답변에 사용했다** (fetch 후 버렸을 수 있다)

이 두 해석 금지는 어떤 실험 결과를 기록할 때도 유지한다.

## 그래서 `machine_score`는 무엇인가

`machine_score`(= `ai` 카테고리, 사용자 질문을 대리한 fetch)는 **"AI 참조 전체"가 아니라
그중 경로 ①로 도달한, 좁고 정직한 표본**이다. 전체 참조량의 하한(lower bound)으로 읽어야 하며,
서비스 간 비교 지표로 쓰면 안 된다 — 경로 ①을 쓰는 서비스(ChatGPT, Claude)가
경로 ②를 쓰는 서비스(소비자 Gemini)보다 참조를 많이 하는 것처럼 보이는 것은
측정 방식의 차이지 실제 참조량의 차이가 아니다.

데이터는 세 층으로 관리된다:

```
machine_events  = 관찰 원본. 모든 fetch가 append-only로 보존된다.
machine_access  = 실측 fetch 횟수. 요청 즉시 누적.
machine_score   = AI attention 해석. 요청 즉시의 잠정값을,
                  밤의 sleep rebuild가 원본에서 재계산해 정본화한다.
```

정본화 규칙: **(agent, record, UTC일) 그룹당 1회**, 그룹 내 최고 confidence × 0.30.
한 대화에서 같은 글을 다섯 번 fetch해도 "그날 이 agent가 이 Record에 관심을 보였다"는
하나의 사실이고, confidence는 그 분류를 얼마나 확신하는가다. access와 score가 의도적으로
갈라지므로(4연타 = access +4, score +0.30), 나중에 "AI가 몇 번 가져갔는가"와
"몇 번의 독립적 관심으로 간주하는가"를 분리해 볼 수 있다.

같은 이유로 **crawler 관측 로그를 프로젝트의 성과 지표로 삼지 않는다.**
이 장치의 가치는 "인터넷의 어떤 자동화된 주체들이 실제로 방문하는가"라는
지형 관찰 자체에 있고, 그 관찰이 타일의 색과 선명도가 된다.

## 통제할 수 있는 것은 여기까지다

AI에게 발견되고, 읽히고, 출처로 식별될 수 있는 웹 자산을 만들어 두는 것까지가 통제 범위다.

1. **발견 가능성** — sitemap, RSS, robots.txt, 독립적인 Record URL, 검색엔진 등록, 외부 링크
2. **가독성** — 본문이 정적 HTML에 존재, 의미 있는 `<title>`/description/heading, 실제 `<a>` 링크
3. **출처 식별성** — 제목·저자(사이트 정체성)·날짜·canonical URL이 HTML 안에 명확히 존재.
   AI가 내용을 가져가더라도 "어디에서 온 내용인지" 식별할 수 있게 하는 것.
   (현재: title/og:site_name/published_time/canonical 구현됨. JSON-LD Article은 미구현 — 선택 레버로 남아 있다.)

그 다음 — 어떤 AI가 언제 어떤 색인을 통해 콘텐츠를 가져가고 실제 답변에 썼는지 — 는
상당 부분 관측 불가능한 영역이며, 그 사실을 받아들이는 것이 이 문서의 요지다.

1. 동일한 Record URL을 Gemini / ChatGPT / Claude / Perplexity에 각각 제공

대조군 (2026-08-24): 접근 실패를 사이트 탓으로 돌리는 외부 분석이 있을 때의 기준 확인 —

몇 초 단위로 작동하는 모습이 실측된 것.

## 경로 ②의 수요가 관측 가능해지는 순간: AI 레퍼럴 유입

경로 ②(색인 기반 응답)의 수요는 서버에서 관측 불가능하다고 정리했지만, 예외가 하나 있다 —
**AI의 인용이 인간의 클릭으로 전환되는 순간**이다. referrer나 `utm_source`(ChatGPT는
인용 링크에 `?utm_source=chatgpt.com`을 붙인다)가 AI 서비스인 `page_view`는 "AI가 이
글을 인용했고, 사람이 따라왔다"는 이중 증거이며, AI가 먼저 인용해야 발생하므로 조작이
어렵다. 이 유입은 machine_score의 두 번째 증거 계급으로 산입된다
((session, record)당 1회 +0.30 — 세션이 곧 시간 단위). 관찰은 `archive_events`의
referrer/search 필드에 이미 쌓이므로, 판정 목록이 바뀌어도 `recompute_machine_scores()`로
소급 재계산된다. 착지(page_view)만 세고 이후의 필드 탐색 클릭은 세지 않는다 —
그건 이미 평범한 인간 열람이다.

**네이버는 판정 목록에서 의도적으로 제외한다.** 네이버 AI의 답변은 검색 결과 페이지에
내장되어 있어 유입 referrer가 일반 검색 클릭과 동일하게 찍힌다(실측: bare `naver.com`
referrer는 AI 브리핑 클릭인지 검색 클릭인지 구별 불가). 게다가 네이버 생태계에는 자기
설치 포인터(본인 블로그의 링크카드)가 있어 자기 유입이 기계 증거로 오분류될 위험이
겹친다. 구별 가능한 신호만 점수화한다 — 구별 불가능한 채널은 인간 열람으로만 계상한다.

## 렌더 연결: 희소 신호는 존재로 렌더한다

실제 로그(30일, 인간 이벤트 890건 / ai 이벤트 7건 중 record 도달 2건)로 시뮬레이션한 결과,
비율 기반 hue는 **전 레코드가 'human'으로 렌더됐다** — 인간 채널은 방문자마다 누적되고
기계 채널은 agent-일당 0.30이라, 크기 비교로는 기계 신호가 렌더에 영구히 도달할 수 없다.
설계가 딛고 있던 두 가설(경로 ① fetch가 충분히 잦다 / 0.30이 인간 점수와 비교 가능한
스케일이다)이 모두 실측 기각된 것이다.

그래서 렌더 연결을 재설계했다: **hue는 인간 관심의 존재만**(테라코타/중립),
**기계 관심은 이산 존재 마커**(타일 우하단 올리브 점, `machineScore ≥ 0.3` = 정본
AI-일 1회 이상)로 표현한다. 희소 신호의 본성에 맞는 렌더는 크기 경쟁이 아니라 존재
표시다. 관측·정본화 계층은 그대로다 — 죽어 있던 것은 점수가 아니라 점수를 인간
점수와 같은 저울에 올린 연결부였다.

마커를 채널별 상대 위상(비율 hue)보다 택한 이유 둘: 두 개의 독립적 사실("인간이
읽는다" / "AI가 관여했다")은 1차원 스펙트럼으로 합치면 서로를 지우고(색 × 점 조합은
네 상태를 전부 보존한다), 상대 정규화는 채널 max를 통해 레코드들의 렌더를 서로
결합시켜 무관한 타일의 색을 흔든다 — 타일의 표현은 그 타일의 관찰에서만 나와야 한다.
**유보 항목**: 마커의 강도 스케일(점 크기·농도를 machineScore 로그 스케일로) — 양에
반응하는 렌더가 필요해질 만큼 machine 증거가 쌓이면 그때 결정한다. 지금은 이산 존재로
충분하다.

human 점수도 같은 원칙으로 정본화한다: `recompute_human_scores()`가
(session, record, event_type)당 1회로 재계산한다(방문 내 반복 가산 실측 13.5% 제거).
세션은 탭과 함께 소멸하는 임시 id — 행위자이자 시간 단위를 겸하므로 machine의
day 축에 해당하는 것이 세션 자체다.

이 시리즈가 남긴 교훈 넷:

1. **AI의 자기 접근 보고는 관측이 아니다.** ChatGPT는 "확인했어"라고 말한 뒤 실제로는
   접근을 시도하지 않았음을 나중에 자인했다. AI가 읽었다/못 읽었다고 말하는 것 자체가
   신뢰할 수 없는 데이터이며, 중재자는 서버 로그뿐이다 — 로그가 AI 주장을 검증하고,
   AI 주장이 로그를 대신하지 못한다. **결과적으로 맞는 자기 보고도 마찬가지다**:
   네이버 AI의 "html_fetcher로 직접 읽었다"는 설명은 답변마다 진술이 이동했고("로그와
   별개로 작동" → "흔적이 남을 수 있지만"), 통제 실험으로 검증되기 전까지는 그럴듯한
   생성물과 구별할 수 없었다.
2. **서비스 단위 일반화도 불가능하다.** ChatGPT-User는 과거(7/23, 7/27) 이 사이트를
   실제 fetch한 기록이 있지만, 이번 시도에서는 정확한 URL을 받고도 fetch하지 않았다.
   같은 서비스가 모드·툴 파이프라인에 따라 경로 ①이기도, 캐시 전용이기도 하다.
   관측은 시도 단위로만 유효하다.
3. **같은 서비스 안에서도 크롤러 경로와 사용자 요청형 fetch 경로는 별개 시스템이다.**
   크롤러는 "이 사이트를 색인해도 되는가"를, 사용자 URL fetcher는 "지금 이 URL에
   요청을 보내도 안전한가"(SSRF·내부망·추적 URL·IP 노출)를 판단한다 — 전자가 YES고
   후자가 NO여도 모순이 아니다. 우리 로그의 증거: GPTBot·ClaudeBot·Meta의 크롤은
   일관되게 성공했고, 심지어 사용자 fetch 경로(ChatGPT-User)도 7/23과 7/27에는
   성공(200, 7/27은 Cloudflare 검증)했다. 따라서 "pages.dev라서 도메인 전체가 위험
   판정된다"는 가설은 기각된다 — 이번 실패는 사용자 fetch 경로의 정책 또는 모드에
   국한된 것이고, 같은 경로도 시점에 따라 갈린다(교훈 ②의 강화). 사이트 구조의
   crawlability 문제가 아니므로 고칠 것은 없다. 실험 기록 시 **어느 접근 경로였는지**
   (크롤러 / 사용자 fetch / 색인)를 구분하는 것이 관측의 일부다.
   (커스텀 도메인의 근거로 쓰였던 "공유 서브도메인 평판 회피"는 이 증거로 미입증
   상태로 강등한다 — 도메인 도입의 남은 근거는 정체성·영속성이다.)
4. **관측되는 것은 자기 식별하는 fetcher뿐이다 — 경로 ①조차 하한선이다.** 네이버 AI
   통제 실험(2026-08-25, post4): 무오염 레코드의 본문을 단어 수준으로 재현했으나
   machine_events·archive_events 모두 무기록. 지금까지 "로그 없음 = 경로 ②③④"로
   추정해 왔지만, 브라우저형 UA의 미검증 fetcher는 직접 fetch(경로 ①)를 하면서도
   비가시다. "로그 없음"에서 접근 경로를 역추론하는 것은 불가능하며, 판정에는 무오염
   콘텐츠 + 원문 대조 + 이중 로그 교차라는 통제 실험이 필요하다.
